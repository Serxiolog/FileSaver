# AMPIS — S1 Auth Service — специализированный промпт v1.0

**Компонент:** S1 — Auth Service. **Статус:** спецификация для будущей независимой реализации, не программный код. **Дата:** 2026-11-18.

## 0. Как применять этот промпт

Ты — Python/FastAPI backend-разработчик, реализующий **только S1** микросервисной системы AMPIS. Перед проектированием и реализацией прочитай эти канонические документы проекта:

1. `MASTER_PROMPT_v1.3.md` — архитектура и правила разработки.
2. `REST_API_CONTRACTS_v1.0.md` — точные HTTP-пути и JSON-ответы.
3. `EVENT_CONTRACTS_v1.0.md` — точные структуры `user.registered` и `user.renamed`.
4. `RABBITMQ_ARCHITECTURE_v1.0.md` — топология и надёжная публикация.

Приоритет у утверждённых REST/Event Contracts. Не изменяй пути, обязательные поля, названия событий, смысл ошибок или ответственность сервисов без явного согласования. Если задача — **спроектировать**, выдавай архитектурное описание; код создавай только после явного запроса на реализацию. Не реализуй G1, S2, S3, S4 или общую инфраструктуру вместо S1.

## 1. Назначение и границы

S1 — **единственный владелец пользователей и учётных данных**. Он регистрирует пользователей, проверяет логин/пароль, выдаёт JWT, возвращает данные авторизованного пользователя и меняет его отображаемое имя. Он публикует изменения профилей в RabbitMQ, чтобы S4 поддерживал актуальную локальную проекцию имён.

S1 **не хранит** файлы, содержимое файлов, download history, счётчики, каталог. Он **не читает** БД других сервисов и не обращается к ним по HTTP для выполнения своих функций. Прямой публичный доступ извне только через G1 Flask.

## 2. Утверждённый стек и контейнеры

- Python; FastAPI; Pydantic; SQLAlchemy 2.x `AsyncEngine` / `AsyncSession`; асинхронный драйвер psycopg 3; Alembic.
- PostgreSQL **B1**, своя БД и свой постоянный Docker volume.
- RabbitMQ, `aio-pika`, `connect_robust`; Transactional Outbox.
- **Два контейнера из одного образа:** `auth-api` (FastAPI) и `auth-worker` (Outbox Publisher). Worker **не является Consumer**: S1 не имеет входящей очереди.
- JWT с подписью **RS256**, время жизни ровно **3600 секунд**; хеширование паролей **Argon2id** с уникальной солью.
- Базовые функциональные тесты: pytest + HTTPX; для async-тестов допустим pytest-asyncio.

## 3. HTTP API S1

Внешние маршруты обслуживаются через G1; соответствующие обработчики и ответы S1 должны удовлетворять `REST_API_CONTRACTS_v1.0.md`.

| Метод | Внешний путь | Доступ | Успешный ответ |
|---|---|---|---|
| `POST` | `/api/auth/register` | Публичный | `201`, `id`, `login`, `display_name`, `created_at` |
| `POST` | `/api/auth/login` | Публичный | `200`, `access_token`, `token_type=bearer`, `expires_in=3600` |
| `GET` | `/api/users/me` | JWT | `200`, `id`, `login`, `display_name`, `created_at`, `updated_at` |
| `PATCH` | `/api/users/me` | JWT | `200`, `id`, `login`, `display_name`, `updated_at` |

Запрос регистрации: JSON `{login, password, display_name}`. Запрос логина: `{login, password}`. Запрос переименования: `{display_name}`. **Регистрация не выполняет автоматический вход.** Нет refresh token в v1. `POST /api/auth/login` выдаёт JWT; браузерный HttpOnly cookie ставит **G1**, а не S1.

Единая форма ошибки: `{ "error": { "code": "...", "message": "...", "request_id": "uuid" } }`. Применять согласованные 401 `INVALID_CREDENTIALS`, 401 `AUTH_REQUIRED`, 409 `LOGIN_ALREADY_EXISTS`, 422 `VALIDATION_ERROR`, 503 `SERVICE_UNAVAILABLE`; не раскрывать подробности о существовании пользователя в ответе на неверный логин.

## 4. Модель данных B1

**User** (минимальные поля):

| Поле | Назначение |
|---|---|
| `id` UUID PK | Идентификатор, равный JWT `sub` |
| `login` | Уникальный логин, индекс/unique constraint |
| `password_hash` | Только Argon2id-хеш, никогда исходный пароль |
| `display_name` | Имя для каталога S4 |
| `created_at`, `updated_at` | UTC |
| `version` | Монотонная версия профиля, начальная `1` |

**OutboxEvent**: `event_id` UUID (уникальный), `event_type`, сериализованная утверждённая оболочка JSON, `created_at`, состояние/время публикации, количество попыток или эквивалентные служебные поля. Не допускать потери события между commit пользователя и публикацией в RabbitMQ.

У каждого сервиса — собственные Alembic-миграции; внешних ключей к B2/B3/B4 нет. Время и ID — в каноническом формате. Политику нормализации логина, допустимые длины имени/пароля и конкретные Argon2id-параметры определить в реализации и отразить в документации; не менять внешний JSON.

## 5. Защита и JWT

- Передача пароля клиент → G1 должна быть защищена HTTPS/TLS при внешнем доступе. Не заменять TLS браузерным SHA-256. Для внутренних соединений G1 ↔ S1 применять предусмотренную проектом защищённую сеть/модель развёртывания; локальный HTTP — только осознанный учебный компромисс.
- На регистрации S1 обрабатывает исходный пароль лишь в памяти, создаёт Argon2id-хеш с уникальной солью и сохраняет **только** `password_hash`. На логине проверяет пароль безопасным verify.
- Не логировать пароли, JWT, ключи подписи и другие секреты; не включать их в RabbitMQ.
- Приватный ключ RS256 существует **только** у S1; публичный ключ получают G1 и защищённые FastAPI-сервисы через конфигурацию/секреты. Не добавлять зависимость от синхронного вызова S1 при каждой проверке токена.
- JWT содержит `sub` (UUID), `iss`, `aud`, `iat`, `exp`; `exp=iat+3600`. Подписывать только согласованным алгоритмом; при проверке фиксировать разрешённый алгоритм, сверять подпись, `exp`, `iss`, `aud` и UUID `sub`.
- За проверку **бизнес-прав** на файлы отвечают S2/S4, не S1.
- Отсутствие refresh token и мгновенного отзыва JWT — утверждённое ограничение первой версии.

## 6. Публикация событий RabbitMQ

Публиковать **только** через Outbox в exchange `domain.events` (durable `topic`), `routing_key = event_type`. Формат — UTF-8 JSON с `content_type=application/json`, persistent.

| Событие | Когда создаётся | Получатель |
|---|---|---|
| `user.registered` | Коммит регистрации | S4 (`reports.events`) |
| `user.renamed` | Коммит смены `display_name` | S4 (`reports.events`) |

Оболочка: `event_id`, `event_type`, `event_version=1`, `aggregate_id=user_id`, `aggregate_version=user.version`, `occurred_at`, `correlation_id`, `payload`. Для обоих событий payload **строго** `{ "user_id": "uuid", "display_name": "строка" }` по `EVENT_CONTRACTS_v1.0.md`; `payload.version` не добавлять. Логин, password hash и JWT в события **не включать**.

В одной транзакции B1: изменить User, повысить `version` (если меняется профиль), сохранить OutboxEvent. Worker асинхронно публикует через `aio-pika`, использует Publisher Confirms и mandatory routing, помечает событие отправленным **после** подтверждения. При потере подтверждения повторно отправлять событие с **тем же** `event_id`.

## 7. Сценарии и сбои

1. Регистрация: валидация → проверка уникальности на уровне БД → Argon2id → `User(version=1)` + `user.registered` в Outbox (один commit) → 201.
2. Вход: найти пользователя → безопасно проверить пароль → подписать JWT → 200; ошибочные учётные данные → единая 401 без утечки пароля.
3. Просмотр профиля: локально проверить JWT → выбрать User по `sub` → 200.
4. Переименование: локально проверить JWT → атомарно обновить имя и `version` → записать `user.renamed` в Outbox → 200.
5. RabbitMQ недоступен: регистрация и переименование коммитятся в B1, события ждут в Outbox и отправятся после восстановления. Не публиковать напрямую из транзакции как единственный способ доставки.
6. S4 недоступен: S1 продолжает работать; события ждут в `reports.events` и впоследствии обновляют проекции.
7. S1 недоступен: сервис не выдаёт новые JWT, но уже выданные токены проверяются G1 и независимыми сервисами локально; публичный каталог/скачивание работают.

## 8. Проектная организация

Рекомендуемое внутреннее разделение: `api/` (роуты), `schemas/` (Pydantic), `domain/` или `services/` (бизнес-операции), `db/` (ORM и сессии), `security/` (Argon2id/JWT), `messaging/` (Outbox Publisher), `alembic/`, `tests/`. Это структура **одной** кодовой базы S1, не дополнительные микросервисы. Не создавать общую БД или общий ORM-модуль с другими сервисами.

Предусмотреть окружение B1 DSN, RabbitMQ URL, JWT issuer/audience, приватный ключ, публичный ключ (если требуется S1 для проверки). Секреты не коммитить. Health/readiness не должны скрывать неисправность БД; Worker должен переживать перезапуск брокера.

## 9. Базовые проверки

- Регистрация пользователя с корректными полями; в B1 отсутствует plaintext password.
- Повторная регистрация с уже занятым логином → 409.
- Успешный логин → корректные `sub`, `exp-iat=3600`, RS256-подпись.
- Неверный пароль → 401; недействительный/просроченный JWT → 401.
- `GET /users/me` и переименование по JWT.
- Два события S1 содержат точные поля, правильные версии и никакие секреты.
- Проверка Outbox при недоступном RabbitMQ; после восстановления событие публикуется повторно с прежним `event_id` при необходимости.

## 10. Критерии готовности

S1 способен независимо стартовать и мигрировать **свою** B1; его API соответствует REST Contract, события — Event Contract; API и Worker запускаются раздельно; пароль защищён, JWT проверяем независимо от S1, события не теряются при временном отказе брокера, функциональные тесты проходят.

**Открытые детали реализации, не требующие решения пользователя сейчас:** точная политика нормализации логинов, минимальная длина пароля, параметры Argon2id, конфигурация ключей и алгоритм подготовки секретов в Docker. Выбирай безопасные разумные значения, документируй их, но не меняй утверждённые контракты.
