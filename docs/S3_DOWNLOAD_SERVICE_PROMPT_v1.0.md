# AMPIS — S3 Download Service — специализированный промпт v1.0

**Компонент:** S3 — Download Service. **Статус:** спецификация для будущей независимой реализации, не программный код. **Дата:** 2026-11-18.

## 0. Роль промпта и канонические источники

Ты — Python/FastAPI-разработчик, реализующий **только S3** проекта AMPIS. Используй одновременно `MASTER_PROMPT_v1.3.md`, `REST_API_CONTRACTS_v1.0.md`, `EVENT_CONTRACTS_v1.0.md`, `RABBITMQ_ARCHITECTURE_v1.0.md`, `OBJECT_STORAGE_ARCHITECTURE_v1.0.md`.

REST/Event Contracts имеют приоритет в отношении форматов. Не меняй события, идентификаторы, маршруты и семантику скачивания; не читай B2, B1 или B4 и не делай синхронный вызов S2 на каждую загрузку/скачивание. Пока пользователь не поручит **реализацию**, работай на уровне проектирования, без генерации кода.

## 1. Назначение S3

S3 — **единственный владелец скачивания содержимого файлов**, учёта успешных загрузок содержимого пользователю, истории, активных сессий и состояния «можно ли начать скачивание». Для этого S3 получает от S2 сведения о файлах через RabbitMQ, локально сохраняет их в B3, читает байты из приватного RustFS и отдаёт клиенту через Flask Gateway G1.

S3 также участвует в протоколе безопасного удаления: после `file.deletion.requested` прекращает создание новых сессий, ожидает завершения уже активных и публикует `file.deletion.ready` в адрес S2.

S3 **не** публикует каталог, не ищет файлы по имени владельца, не выдаёт отчёт, не изменяет файл и не удаляет объекты из RustFS.

## 2. Стек и изоляция

- FastAPI + Pydantic; SQLAlchemy 2.x AsyncSession с psycopg 3 async; Alembic; своя PostgreSQL **B3**.
- RabbitMQ: `aio-pika`, `connect_robust`, durable `domain.events` topic, отдельная очередь `download.events`, Transactional Outbox, manual ACK, идемпотентность.
- RustFS: только `GetObject` (опционально `HeadObject`) из приватного `user-files` через **отдельные credentials S3 без Put/Delete**; `boto3` синхронный, выносить блокирующий I/O из event loop.
- Один образ на два контейнера: `download-api` (HTTP/streaming), `download-worker` (Consumer + Outbox Publisher). Они имеют общую B3, но не общую БД с остальными микросервисами.
- JWT RS256 проверяется локально, если присутствует; публичное скачивание разрешено **без токена**. Если клиент передал некорректный токен, не доверять его `sub` и не записывать поддельный `user_id`.

## 3. HTTP API

**Единственный пользовательский REST-маршрут S3:** `GET /api/files/{file_id}/download` (через G1). При успехе `200` и **бинарное тело**, а не JSON:

```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
Content-Length: 716800

<binary content>
```

Для Unicode-имён и HTTP-заголовков требуется безопасный `filename*`/RFC-совместимое кодирование и очистка ненадёжного имени. Внешний URL остаётся G1 URL; **не** возвращать presigned RustFS URL. G1 не должен принудительно буферизовать весь скачиваемый файл.

- Без JWT: скачивание анонимное, `DownloadSession.user_id = null`.
- С действительным JWT: `user_id = sub` из **проверенного** токена; не обращаться к S1.
- До выдачи байтов проверить локальную запись файла и `status=AVAILABLE`.
- Неуведомлённый S3 о новом файле временно может отвечать 404/недоступностью согласно REST Contract: eventual consistency после загрузки в S2 допустима.
- `DRAINING` — отказ в **новой** сессии (`FILE_NOT_AVAILABLE`, HTTP 409), `DELETED` — `FILE_DELETED`/410; неизвестный UUID — 404. Ошибки общей формы `{ "error": { "code": "...", "message": "...", "request_id": "uuid" } }`.
- `GET /api/files/{file_id}` **не** обрабатывается S3: отдельную карточку и каталог обслуживает S4, и их просмотр не увеличивает счётчик.

## 4. Модель данных B3

**AvailableFile** — собственная проекция событий S2:

| Поле | Назначение |
|---|---|
| `file_id` UUID PK | Логическая ссылка на файл S2, без межбазового FK |
| `storage_key` | Ключ объекта в `user-files` |
| `status` | `AVAILABLE`, `DRAINING`, `DELETED` |
| `file_version` | Наибольшая применённая `aggregate_version` состояния файла |
| `original_name`, `content_type`, `size_bytes` | Читаемые метаданные из `file.created`, необходимые для безопасного Content-Disposition/Content-Type/Length |
| `deletion_request_id` | Текущая согласуемая операция удаления, если есть |

Добавление метаданных в B3 — допустимая **внутренняя** детализация проекции, поскольку они уже присутствуют в каноническом `file.created`; внешнее событие не изменять.

**DownloadSession**: `session_id`, `file_id`, `user_id NULL`, `status`, `started_at`, `finished_at`, `lease_expires_at`. Состояние/аренду моделировать так, чтобы по БД можно было определить реальные активные передачи и корректно восстановиться после краша.

**DownloadHistory**: `download_id` (уникальный), `file_id`, `user_id NULL`, `completed_at`. Запись об успешном завершении серверной передачи.

**ProcessedEvent**: `event_id` unique; **OutboxEvent**: хранит `file.downloaded` и `file.deletion.ready`, пока не подтверждена публикация. Индексы по `file_id`/состоянию сессии и ограничения уникальности необходимы.

Не держать долгую транзакцию БД открытой на время потоковой передачи. Не хранить содержимое файлов в B3.

## 5. Входящие и исходящие события

| Направление | Событие | Назначение |
|---|---|---|
| Входящее | `file.created` от S2 | Создать/обновить AvailableFile, открыть AVAILABLE только при отсутствии более нового состояния |
| Входящее | `file.deletion.requested` от S2 | Перевести файл в DRAINING, запретить новые сессии |
| Входящее | `file.deleted` от S2 | Зафиксировать DELETED/tombstone |
| Исходящее | `file.downloaded` → S4 | Успешная серверная передача, уникальный download_id |
| Исходящее | `file.deletion.ready` → S2 | Безопасно завершены активные передачи данного deletion_request_id |

Имена и JSON payload **строго** из `EVENT_CONTRACTS_v1.0.md`. `aggregate_version` у входящих событий состояния из S2 (1/2/3 в стандартном потоке) защищает от старых событий. У `file.downloaded` и `file.deletion.ready` значение `aggregate_version=null`. `file.downloaded.payload` содержит `download_id`, `file_id`, `user_id|null`, `completed_at`. У `file.deletion.ready` — `file_id`, `deletion_request_id`; сохранять общий `correlation_id` операции удаления.

Использовать Transactional Outbox для исходящих событий. Входящее событие + `processed_events(event_id)` фиксировать в **одной транзакции B3**, ACK — только после commit. При повторной доставке ACK без повторного эффекта; при несовместимой схеме — контролируемая DLQ, не бесконечный requeue.

**Порядок событий не гарантирован.** `file.deletion.requested` может прийти до `file.created`. Сохранять tombstone/placeholder с максимальной версией и не возвращать файл в AVAILABLE после более новой версии. `file.deleted` также не должен быть «отменён» запоздалым созданием.

## 6. Сценарий скачивания

1. G1 → S3 с `file_id` и, при наличии, JWT. S3 независимо валидирует токен.
2. В **короткой атомарной транзакции B3** проверить `AvailableFile.status=AVAILABLE` и зарегистрировать DownloadSession. Операция регистрации и перевод файла в DRAINING должны быть сериализованы относительно друг друга: нельзя разрешить начало сессии после подтверждённого перехода в DRAINING.
3. Получить поток через `boto3.GetObject` из RustFS; передавать байты через G1 с корректным закрытием ресурсов.
4. По окончании успешной **серверной** передачи закрыть сессию; в одной транзакции записать DownloadHistory и Outbox `file.downloaded`. Один логический download — один `download_id`.
5. Если передача оборвалась, запись успешного скачивания и `file.downloaded` **не создавать**. Сессию корректно завершить/пометить неуспешной.
6. Если сессия была последней активной в состоянии DRAINING, инициировать проверку безопасной готовности удаления, затем Outbox `file.deletion.ready`.

Уточнение границы успешности: сервер считает успешной законченную отдачу через S3/G1; система **не** может доказать запись файла на диск конечного клиента. Не считать простое чтение RustFS или открытие GET достаточным основанием для увеличения счётчика.

## 7. Безопасное удаление и leases

**Инвариант:** S3 публикует `file.deletion.ready` **только** для текущего `deletion_request_id` и лишь тогда, когда новые сессии запрещены, а все уже начатые передачи **реально завершены или гарантированно остановлены**.

- При `file.deletion.requested`: транзакционно менять status AVAILABLE→DRAINING. Если активных сессий нет, Outbox ready можно создать сразу; если есть — ждать безопасного завершения последней.
- Системная уборка/проверка восстанавливает зависшие DownloadSession после аварии Worker/API и позволяет корректно досогласовать удаление.
- **Истёкший lease сам по себе не доказывает прекращение реально работающего stream.** Прежде чем считать сессию завершённой, нужен протокол heartbeat/прекращения передачи или иной доказуемо безопасный способ; этот механизм подробно определить при реализации S3.
- ACK событий только после локального commit; публикация ready через Outbox с сохранением event_id при ретраях.
- При `file.deleted` сохранить DELETED/tombstone, не принимать новые сессии и не возрождать файл запоздалым `file.created`.
- История успешных скачиваний сохраняется в B3 независимо от удаления бинарного объекта.

## 8. Отказоустойчивость

- S2 выключен: скачивание **уже известных AVAILABLE** файлов работает по локальной B3 и RustFS, без SQL/HTTP обращения в S2.
- S1 выключен: анонимные и авторизованные скачивания с ранее выданным валидным JWT работают без обращения в S1.
- S4 выключен: скачивание работает; `file.downloaded` накапливаются в `reports.events` после Outbox-публикации.
- RabbitMQ недоступен: S3 продолжает обслуживать известные файлы, записи `file.downloaded` ждут в Outbox; события удаления догоняют позже.
- RustFS недоступен: операция скачивания получает согласованную ошибку, не считается успешной; другие сервисы работают.
- С3 перезапущен во время передачи: незавершённые сессии восстанавливаются/безопасно завершаются; нельзя разрешать S2 удалить объект, пока реально идёт передача.

## 9. Рекомендуемая внутренняя структура

`api/`, `schemas/`, `domain/` или `services/`, `db/`, `streaming/`, `storage/` (read-only S3 client), `messaging/` (Inbox/Outbox), `alembic/`, `tests/`. В отдельном `download-worker` объединять controlled consumer и outbox publisher; не запускать Consumer в каждом HTTP-процессе.

Конфигурация: B3 DSN, RabbitMQ URL, RustFS endpoint/bucket/read-only credentials, JWT public key, issuer/audience, параметры worker. Не логировать JWT или объекты; логировать `file_id`, `session_id`, `event_id`, `request_id`.

## 10. Базовые тесты

- Публичное скачивание известного файла возвращает исходные байты и корректное имя; JWT необязателен.
- Авторизованное скачивание пишет `user_id` из JWT; гость — `null`.
- Успешная серверная передача создаёт **ровно один** DownloadHistory и один `file.downloaded`.
- Оборванная/ошибочная передача не создаёт успешную историю.
- Повторное событие `file.created` безопасно; запоздалое `file.created` после DRAINING/DELETED не открывает файл снова.
- После `file.deletion.requested` новые скачивания запрещены; старое активное завершается, только затем публикуется правильный `file.deletion.ready`.
- Проверка конкуренции: начало сессии vs DRAINING не нарушает инвариант.
- При остановленном S2 доступные файлы скачиваются; при остановленном RabbitMQ Outbox сохраняет факты скачиваний.
- Во время отказа RustFS не появляются ложные `file.downloaded`.

## 11. Критерии готовности

S3 независимо запускается и мигрирует B3, потребляет только нужные события файлов, читает RustFS с read-only правами, отдаёт бинарный поток через G1, считает только завершённые серверные передачи, публикует события через Outbox и надёжно запрещает новые скачивания при удалении.

**Открытая техническая деталь, требующая особенного внимания при реализации:** реальная семантика завершения stream и восстановления lease/heartbeat после сбоя — её нельзя «решить» одной проверкой времени в БД. Внешний контракт от этого не меняется.
