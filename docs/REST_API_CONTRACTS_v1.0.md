# AMPIS — REST API CONTRACTS v1.0

**Статус:** согласованный контракт перед реализацией. **Дата:** 2026-11-18.  
**Основной документ:** `MASTER_PROMPT_v1.3.md`. События: `EVENT_CONTRACTS_v1.0.md`.

## 1. Общие соглашения

- Внешняя точка входа — **G1 Flask**: `/api/...` для REST и `/app/...` для HTML (Jinja2). Внутренние HTTP-эндпоинты FastAPI доступны только через внутреннюю Docker-сеть; G1 сопоставляет внешние маршруты целевым S1–S4.
- Все идентификаторы пользователя, файла, скачивания и операции — UUID-строки. Даты — ISO 8601 в UTC (`Z`). Имена полей JSON — `snake_case`.
- Успешные ответы возвращают данные непосредственно, без обёртки `data`. Ошибки имеют общее поле `error`. Исключение из JSON: загрузка (`multipart/form-data`) и скачивание (бинарный поток).
- Аутентификация: JWT RS256, срок 3600 секунд, UUID пользователя в `sub`; G1 и защищённые сервисы самостоятельно проверяют подпись, `exp`, `iss`, `aud`.
- В браузере токен находится в HttpOnly, Secure, SameSite cookie **при HTTPS**, изменяющие операции защищаются от CSRF. Для API-клиентов разрешён `Authorization: Bearer <jwt>`. G1 извлекает токен из cookie либо доверенного заголовка и передаёт его в заголовке Authorization целевому сервису. Не доверять клиентским `X-User-Id`.
- Регистрация и вход передают пароль **только через защищённое TLS/HTTPS соединение с G1**. На стороне S1 пароль хешируется алгоритмом Argon2id с уникальной солью; исходный пароль не хранится, не логируется, не публикуется. Простое браузерное хеширование вместо TLS **не используется**. В локальной изолированной Docker-сети внутренний HTTP допустим в рамках учебной конфигурации; это не TLS-защита, при внешнем развёртывании модель внутренних соединений должна быть защищена.
- Публичные `GET` каталога, карточки файла и скачивание не требуют JWT. Наличие JWT для публичного скачивания позволяет записать `user_id`, но отсутствие JWT допускается (`user_id = null`).
- Лимит содержимого файла: не более **1 048 576 байт включительно** (в нашей реализации «1 МБ» = 1 МиБ). Проверять реальный поток на S2, а в G1 учитывать дополнительные байты multipart-обёртки. `storage_key` не раскрывается во внешнем API.
- Пагинация: `page >= 1`, `size` от 1 до 100, по умолчанию `page=1`, `size=20`. Сортировка стабильная с вторичным ключом `file_id`.
- `request_id` — UUID запроса, созданный G1 или поддерживаемый сквозным контекстом; применяется для диагностики. Пользовательский `request_id` не является идентификатором безопасности.

## 2. Матрица маршрутов

| Метод | Внешний путь | Владелец | Доступ | Успех |
|---|---|---|---|---|
| POST | `/api/auth/register` | S1 | публичный | 201 JSON |
| POST | `/api/auth/login` | S1 | публичный | 200 JSON / cookie в браузерном сценарии |
| GET | `/api/users/me` | S1 | JWT | 200 JSON |
| PATCH | `/api/users/me` | S1 | JWT | 200 JSON |
| POST | `/api/files` | S2 | JWT | 201 JSON |
| DELETE | `/api/files/{file_id}` | S2 | владелец | 202 JSON |
| GET | `/api/files/{file_id}/download` | S3 | публичный | 200 бинарный поток |
| GET | `/api/files` | S4 | публичный | 200 JSON |
| GET | `/api/files/{file_id}` | S4 | публичный | 200 JSON |
| GET | `/api/files/{file_id}/stats` | S4 | владелец | 200 JSON |

Внешние `/app/login`, `/app/register` и прочие HTML-маршруты обслуживает Flask и не следует считать отдельным публичным микросервисным API.

## 3. S1 — пользователи

### POST `/api/auth/register`

**Request** (`application/json`):
```json
{
  "login": "alex123",
  "password": "MySecurePassword123!",
  "display_name": "Александр"
}
```

**201 Created:**
```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "login": "alex123",
  "display_name": "Александр",
  "created_at": "2026-11-18T12:00:00Z"
}
```

Создание профиля не выдаёт JWT автоматически. При успешной регистрации S1 сохраняет `user.registered` в Outbox. Логин уникален. Пароль есть только в защищённом теле запроса и обрабатывается S1 с помощью Argon2id; в базе остаётся `password_hash`.

### POST `/api/auth/login`

**Request:**
```json
{
  "login": "alex123",
  "password": "MySecurePassword123!"
}
```

**200 OK** (REST-клиент):
```json
{
  "access_token": "<signed-jwt>",
  "token_type": "bearer",
  "expires_in": 3600
}
```

В сценарии Web UI Flask принимает токен от S1 и устанавливает HttpOnly cookie с надлежащими атрибутами; токен не выводится в браузерный JavaScript. Конкретная серверная форма HTML-ответа G1 не меняет JSON-контракт S1. Refresh token в v1 нет.

### GET `/api/users/me`

JWT обязателен. **200 OK:**
```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "login": "alex123",
  "display_name": "Александр",
  "created_at": "2026-11-18T12:00:00Z",
  "updated_at": "2026-11-18T12:00:00Z"
}
```

### PATCH `/api/users/me`

JWT обязателен. **Request:**
```json
{
  "display_name": "Александр Иванов"
}
```

**200 OK:**
```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "login": "alex123",
  "display_name": "Александр Иванов",
  "updated_at": "2026-11-18T12:15:00Z"
}
```

После изменения S1 публикует `user.renamed` через Outbox; S4 асинхронно обновляет имя в своей проекции. UUID пользователя остаётся прежним.

## 4. S2 — загрузка и удаление

### POST `/api/files`

JWT обязателен. **Request:** `multipart/form-data`, единственное обязательное поле `file` — содержимое файла (не JSON). `owner_id` клиент не задаёт: он вычисляется из проверенного `JWT.sub`.

**201 Created:**
```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "owner_id": "11111111-1111-4111-8111-111111111111",
  "original_name": "report.pdf",
  "size_bytes": 716800,
  "content_type": "application/pdf",
  "status": "ACTIVE",
  "created_at": "2026-11-18T12:30:00Z"
}
```

S2 записывает объект в RustFS, затем фиксирует метаданные и `file.created` в локальной транзакции B2/Outbox. После ответа 201 локальная запись ACTIVE существует, но её репликация в S3 и S4 может занять некоторое время. В случае превышения 1 МиБ — HTTP 413. Одинаковые исходные имена не означают одинаковые UUID.

### DELETE `/api/files/{file_id}`

JWT обязателен; S2 проверяет `JWT.sub == file.owner_id`. **202 Accepted:**
```json
{
  "file_id": "22222222-2222-4222-8222-222222222222",
  "deletion_request_id": "44444444-4444-4444-8444-444444444444",
  "status": "DELETING",
  "message": "File deletion has been scheduled"
}
```

Действует протокол `ACTIVE → DELETING → DELETED`, с подтверждением S3 (`file.deletion.ready`) перед физическим `DeleteObject`. Повторный DELETE на стадии DELETING возвращает те же `deletion_request_id` и статус, не создавая вторую операцию. Для уже DELETED можно вернуть 410 или идемпотентный результат при повторе той же операции; конкретное поведение повторного вызова после завершения уточняется в специализированном контракте S2, не менять переходы состояний.

## 5. S3 — скачивание

### GET `/api/files/{file_id}/download`

Публичный запрос. **200 OK** — поток байтов, не JSON:
```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
Content-Length: 716800

<binary content>
```

Для Unicode-имён файлов использовать безопасный `filename*`; заголовки от недоверенного имени очищаются. Браузер получает поток через G1, который не буферизует весь ответ без необходимости. S3 разрешает скачивание только при локальном статусе `AVAILABLE`, создаёт и завершает DownloadSession в B3, записывает успешную серверную передачу в DownloadHistory и `file.downloaded` в Outbox. S3 не может доказать, что клиент физически сохранил файл; счётчик отражает успешно завершённую передачу на стороне сервера. Просмотр карточки не считается скачиванием. Во время `DRAINING` новые сессии запрещены.

## 6. S4 — каталог и статистика

### GET `/api/files`

Публично. Параметры запроса: `name` — подстрока имени файла; `owner` — подстрока отображаемого имени владельца; `sort` — `name | owner | downloads`; `order` — `asc | desc`; `page`, `size`. По умолчанию `sort=name`, `order=asc`, `page=1`, `size=20`. Для равных значений сортировки дополнительный ключ `file_id` гарантирует детерминированный порядок.

**Пример:** `GET /api/files?name=report&sort=downloads&order=desc&page=1&size=20`

**200 OK:**
```json
{
  "items": [
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "original_name": "report.pdf",
      "owner": {
        "id": "11111111-1111-4111-8111-111111111111",
        "display_name": "Александр Иванов"
      },
      "size_bytes": 716800,
      "download_count": 42,
      "download_url": "/api/files/22222222-2222-4222-8222-222222222222/download",
      "created_at": "2026-11-18T12:30:00Z"
    }
  ],
  "page": 1,
  "size": 20,
  "total": 1,
  "pages": 1
}
```

При отсутствии результатов `items=[]`, `total=0`, `pages=0`. Только активные файлы включаются в публичный каталог по известному S4 состоянию. S4 не запрашивает данные у S1/S2/S3 синхронно; обновления приходят через события RabbitMQ.

### GET `/api/files/{file_id}`

Публичная **карточка метаданных**, не скачивание; **не увеличивает** `download_count`.

**200 OK:**
```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "original_name": "report.pdf",
  "owner": {
    "id": "11111111-1111-4111-8111-111111111111",
    "display_name": "Александр Иванов"
  },
  "size_bytes": 716800,
  "download_count": 42,
  "created_at": "2026-11-18T12:30:00Z",
  "download_url": "/api/files/22222222-2222-4222-8222-222222222222/download"
}
```

После `file.deletion.requested` S4 скрывает файл из публичной карточки и списка. Для скрытого или неизвестного файла публичный метод возвращает 404. Проекции с прошлой статистикой можно сохранять в B4, не раскрывая их публике.

### GET `/api/files/{file_id}/stats`

JWT владельца. S4 сверяет `JWT.sub` с локальным `FileCatalogProjection.owner_id`; не обращается в S2 или S1. **200 OK:**
```json
{
  "file_id": "22222222-2222-4222-8222-222222222222",
  "original_name": "report.pdf",
  "download_count": 42,
  "downloaded_by": [
    {
      "user_id": "33333333-3333-4333-8333-333333333333",
      "display_name": "Мария"
    },
    {
      "user_id": "55555555-5555-4555-8555-555555555555",
      "display_name": "Дмитрий"
    }
  ]
}
```

По ТЗ отчёт содержит количество скачиваний (включая анонимные и повторные) и **имена зарегистрированных пользователей**, скачавших файл. `downloaded_by` содержит уникальных зарегистрированных пользователей (по `user_id`), имена берутся из локальных профилей S4; гости учитываются в `download_count`, но не имеют имени и не добавляются в `downloaded_by`. Дополнительные счётчики по гостям/каждому пользователю и полный журнал дат не нужны для v1. Исторические данные можно хранить после удаления файла; доступ к ним всё равно проверяется по владельцу.

## 7. Единый контракт ошибок

**Структура:**
```json
{
  "error": {
    "code": "FILE_ACCESS_DENIED",
    "message": "You cannot delete a file owned by another user",
    "request_id": "66666666-6666-4666-8666-666666666666"
  }
}
```

| HTTP | `error.code` | Пример ситуации |
|---|---|---|
| 400 | `INVALID_REQUEST` | Некорректная структура запроса |
| 401 | `AUTH_REQUIRED` | Отсутствующий, просроченный или неверный JWT |
| 401 | `INVALID_CREDENTIALS` | Неверный логин или пароль |
| 403 | `FILE_ACCESS_DENIED` | Чужой файл при DELETE/статистике |
| 404 | `FILE_NOT_FOUND` | Неизвестный/скрытый из публичного каталога файл |
| 409 | `LOGIN_ALREADY_EXISTS` | Логин занят |
| 409 | `FILE_NOT_AVAILABLE` | Запрос скачивания на стадии DRAINING |
| 410 | `FILE_DELETED` | S3 знает, что файл окончательно удалён |
| 413 | `FILE_TOO_LARGE` | Содержимое превышает 1 МиБ |
| 422 | `VALIDATION_ERROR` | Некорректные значения или типы полей |
| 503 | `SERVICE_UNAVAILABLE` | Недоступен требуемый сервис, БД или Object Storage |

FastAPI и Flask должны отдавать согласованный формат ошибок, включая валидацию. Ошибки доступа не раскрывают внутренние credentials или чужие данные. Запросы к одному сервису не должны зависеть от доступности независимых сервисов.

## 8. Согласованные ограничения и критерии проверки

- Создание файла доступно только с JWT, скачивание и каталог публичные; просмотр метаданных сам по себе не создаёт записи скачивания.
- Только владелец может удалять файл и получать закрытую статистику (JWT.sub == owner_id из локальной БД соответствующего сервиса).
- Поиск/сортировка/пагинация выполняются в S4; ни G1, ни S4 не сканируют RustFS для построения каталога.
- Прямые ссылки Object Storage не публикуются; `download_url` указывает на G1.
- При временной недоступности S1 публичный просмотр и скачивание продолжают работать; при недоступности S2 старые файлы можно скачивать через S3.
- Реализация независимых сервисов обязана сверяться с этой спецификацией; изменение формата требует явной новой версии контракта.

## 9. Необязательные детали, оставленные до реализации

Точные ограничения длины `login`/`display_name`, политика сильных паролей, список допустимых MIME-типов (файлы произвольные), метрики и дополнительные HTTP-заголовки, механика CSRF-токена и конкретная реализация потоковой передачи. Они не должны менять зафиксированные поля, маршруты и безопасность.
