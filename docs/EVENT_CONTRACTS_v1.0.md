# AMPIS — EVENT CONTRACTS v1.0

**Статус:** согласованные доменные сообщения RabbitMQ. **Дата:** 2026-11-18.  
**Связанные документы:** `MASTER_PROMPT_v1.3.md`, `RABBITMQ_ARCHITECTURE_v1.0.md`, `REST_API_CONTRACTS_v1.0.md`.

## 1. Транспорт и маршрутизация

- RabbitMQ / AMQP 0-9-1, библиотека **aio-pika**, `domain.events` (durable topic exchange), `routing_key = event_type`.
- Persistent JSON-сообщения, `content_type=application/json`, UTF-8.
- Очереди: `upload.events` (S2), `download.events` (S3), `reports.events` (S4). S1 только публикует события через Outbox; входящая очередь S1 не требуется.
- Все очереди/точные bindings должны быть созданы **до** публикации. Durable queues, Publisher Confirms, mandatory routing, ручной ACK после БД commit, Transactional Outbox и дедупликация по event_id.
- Протокол — at-least-once; сообщения могут повторяться, приходить позже и в ином порядке. Для репликации состояния использовать версии сущностей и локальные tombstones. События не содержат секреты, пароли, JWT или байты файлов.

| `event_type` | Publisher | Consumer |
|---|---|---|
| `user.registered` | S1 | S4 |
| `user.renamed` | S1 | S4 |
| `file.created` | S2 | S3, S4 |
| `file.deletion.requested` | S2 | S3, S4 |
| `file.deletion.ready` | S3 | S2 |
| `file.deleted` | S2 | S3, S4 |
| `file.downloaded` | S3 | S4 |

S4 не получает техническое подтверждение `file.deletion.ready` и не публикует доменные события в v1.

## 2. Общая JSON-оболочка

```json
{
  "event_id": "70000000-0000-4000-8000-000000000001",
  "event_type": "user.registered",
  "event_version": 1,
  "aggregate_id": "11111111-1111-4111-8111-111111111111",
  "aggregate_version": 1,
  "occurred_at": "2026-11-18T12:00:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000001",
  "payload": {}
}
```

- `event_id`: UUID **факта**. При повторной публикации записи Outbox UUID не меняется.
- `event_type`: один из перечисленных типов, одновременно routing key.
- `event_version`: версия схемы JSON, в v1 всегда `1`.
- `aggregate_id`: UUID пользователя или файла, к которому относится событие.
- `aggregate_version`: номер версии **состояния** сущности при регистрации, переименовании, создании, начале и завершении удаления файла; `null` у фактов `file.downloaded`, `file.deletion.ready`.
- `occurred_at`: UTC ISO 8601, момент возникновения события.
- `correlation_id`: UUID пользовательской операции/цепочки; связанные события удаления сохраняют исходный correlation_id.
- `payload`: тело, специфичное для типа события.

`payload.version` **не используется**: версия состояния находится в `aggregate_version`, чтобы исключить расхождения. Это уточнение заменяет предварительные примеры `RABBITMQ_ARCHITECTURE_v1.0.md`.

## 3. События S1

### 3.1 `user.registered` → S4

```json
{
  "event_id": "70000000-0000-4000-8000-000000000001",
  "event_type": "user.registered",
  "event_version": 1,
  "aggregate_id": "11111111-1111-4111-8111-111111111111",
  "aggregate_version": 1,
  "occurred_at": "2026-11-18T12:00:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000001",
  "payload": {
    "user_id": "11111111-1111-4111-8111-111111111111",
    "display_name": "Александр"
  }
}
```

S4 создаёт/обновляет `UserProfileProjection` только если версия новее локальной, не затирая позднее переименование.

### 3.2 `user.renamed` → S4

```json
{
  "event_id": "70000000-0000-4000-8000-000000000002",
  "event_type": "user.renamed",
  "event_version": 1,
  "aggregate_id": "11111111-1111-4111-8111-111111111111",
  "aggregate_version": 2,
  "occurred_at": "2026-11-18T12:15:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000002",
  "payload": {
    "user_id": "11111111-1111-4111-8111-111111111111",
    "display_name": "Александр Иванов"
  }
}
```

Переименование не изменяет UUID владельца загруженных файлов. Событие может прийти до `user.registered`; версия не даёт откатить имя назад.

## 4. События S2

### 4.1 `file.created` → S3, S4

```json
{
  "event_id": "70000000-0000-4000-8000-000000000003",
  "event_type": "file.created",
  "event_version": 1,
  "aggregate_id": "22222222-2222-4222-8222-222222222222",
  "aggregate_version": 1,
  "occurred_at": "2026-11-18T12:30:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000003",
  "payload": {
    "file_id": "22222222-2222-4222-8222-222222222222",
    "owner_id": "11111111-1111-4111-8111-111111111111",
    "original_name": "report.pdf",
    "size_bytes": 716800,
    "content_type": "application/pdf",
    "storage_key": "files/22222222-2222-4222-8222-222222222222",
    "created_at": "2026-11-18T12:30:00Z"
  }
}
```

S3 обновляет реестр файлов в B3 (`file_id → storage_key`), S4 обновляет каталог и владельца. Не помещать исходные байты в payload. Событие не должно возвращать файл в ACTIVE/AVAILABLE после уже известного более нового состояния удаления.

### 4.2 `file.deletion.requested` → S3, S4

```json
{
  "event_id": "70000000-0000-4000-8000-000000000004",
  "event_type": "file.deletion.requested",
  "event_version": 1,
  "aggregate_id": "22222222-2222-4222-8222-222222222222",
  "aggregate_version": 2,
  "occurred_at": "2026-11-18T15:00:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000004",
  "payload": {
    "file_id": "22222222-2222-4222-8222-222222222222",
    "deletion_request_id": "44444444-4444-4444-8444-444444444444",
    "requested_at": "2026-11-18T15:00:00Z"
  }
}
```

S3 атомарно переводит файл в DRAINING, запрещает новые сессии скачивания и дожидается завершения зарегистрированных. S4 скрывает файл из публичного каталога. Если `file.created` задержалось, состояние удаления сохраняется как tombstone, а запоздалое `file.created` не открывает доступ вновь.

### 4.3 `file.deleted` → S3, S4

```json
{
  "event_id": "70000000-0000-4000-8000-000000000005",
  "event_type": "file.deleted",
  "event_version": 1,
  "aggregate_id": "22222222-2222-4222-8222-222222222222",
  "aggregate_version": 3,
  "occurred_at": "2026-11-18T15:02:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000004",
  "payload": {
    "file_id": "22222222-2222-4222-8222-222222222222",
    "deletion_request_id": "44444444-4444-4444-8444-444444444444",
    "deleted_at": "2026-11-18T15:02:00Z"
  }
}
```

Событие означает, что S2 подтвердил физическое удаление из RustFS. S3 и S4 завершают локальную модель удаления. История скачиваний/статистика может сохраняться отдельно от публичного каталога.

## 5. События S3

### 5.1 `file.downloaded` → S4

```json
{
  "event_id": "70000000-0000-4000-8000-000000000006",
  "event_type": "file.downloaded",
  "event_version": 1,
  "aggregate_id": "22222222-2222-4222-8222-222222222222",
  "aggregate_version": null,
  "occurred_at": "2026-11-18T12:50:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000005",
  "payload": {
    "download_id": "88888888-8888-4888-8888-888888888888",
    "file_id": "22222222-2222-4222-8222-222222222222",
    "user_id": "33333333-3333-4333-8333-333333333333",
    "completed_at": "2026-11-18T12:50:00Z"
  }
}
```

Анонимное скачивание передаётся как `"user_id": null`. S4 уникально учитывает `download_id`, считает общее число успешных скачиваний и формирует список уникальных зарегистрированных пользователей. Повторное событие не прибавляет счётчик вторично. При получении `file.downloaded` до `file.created` факт не теряется и учитывается после формирования каталожной проекции. Имена отображаются по актуальным событиям S1.

### 5.2 `file.deletion.ready` → S2

```json
{
  "event_id": "70000000-0000-4000-8000-000000000007",
  "event_type": "file.deletion.ready",
  "event_version": 1,
  "aggregate_id": "22222222-2222-4222-8222-222222222222",
  "aggregate_version": null,
  "occurred_at": "2026-11-18T15:01:00Z",
  "correlation_id": "60000000-0000-4000-8000-000000000004",
  "payload": {
    "file_id": "22222222-2222-4222-8222-222222222222",
    "deletion_request_id": "44444444-4444-4444-8444-444444444444"
  }
}
```

S2 принимает подтверждение только для активного `deletion_request_id`. S3 отправляет его лишь после запрета новых скачиваний и безопасного завершения/остановки всех реально активных передач. S2 после этого выполняет идемпотентный DeleteObject и публикует `file.deleted`.

## 6. Транзакционные и эксплуатационные гарантии

1. **Outbox:** изменение локальной БД и событие Outbox сохраняются одним commit. Издатель публикует событие, дожидается Publisher Confirm и только тогда отмечает запись отправленной. При повторной отправке сохраняет первоначальный `event_id`.
2. **Inbox / processed_events:** получатель в одной транзакции обновляет свои данные и записывает уникальный `event_id`; ACK отправляется **после** commit. На дубликат — ACK без повторного бизнес-эффекта.
3. **Порядок:** применять только более новую `aggregate_version` в проекции состояния. Для `file.downloaded` и `file.deletion.ready` использовать уникальные `download_id` / `deletion_request_id` и модель состояний, а не отдельную aggregate_version.
4. **Ошибки:** временные ошибки обрабатываются ограниченными повторами с задержкой; необрабатываемые сообщения направляются в DLQ. Не допускать бесконечного `nack(requeue=True)`; схема retry-политик и лимиты конкретизируются в инфраструктурном этапе.
5. **Сбой S4:** события накапливаются в `reports.events`; после восстановления S4 автоматически достраивает каталог и статистику. При недоступном S1 публичные S3/S4 не требуют синхронного вызова S1.
6. **Удаление:** `file.deletion.requested` → S3 DRAINING → `file.deletion.ready` → S2 DeleteObject → `file.deleted`. С2 не удаляет физический объект без подтверждения S3.

## 7. Границы v1

Схемы **этих семи событий утверждены**. Изменение обязательных полей, типов или семантики требует согласования и новой версии схемы. Конкретные retry-параметры, количество одновременных consumers и настройки RabbitMQ DLX уточняются при написании Docker/Worker. Эти детали не меняют контракты событий.
