# Эксплуатация локальной AMPIS

## Проверенное окружение

CachyOS/Linux x86_64, Docker Engine 29.9.3, Docker Compose 5.7.1.
Точные digest инфраструктуры находятся в `infrastructure/images.json`;
точные Python-пакеты — в `requirements.lock` соответствующего приложения.
Приложения запускаются под UID/GID пользователя хоста, JWT private key имеет
права 0600 и монтируется только в auth-api. Worker S1 ключ подписи не получает.
Внешний адрес ограничен loopback, HTTP разрешён как локальная учебная среда.
Для внешнего доступа необходимо настроить HTTPS, Secure cookies и модель TLS.

## Первоначальная настройка и повторный запуск

`python infrastructure/start.py` выполняет сборку, остановку workers перед
перенастройкой, запуск инфраструктуры, bootstrap аккаунтов/топологии и IAM,
а затем запуск всех 15 контейнеров с ожиданием readiness.
RabbitMQ hostname фиксирован: rabbitmq. Его volume хранит пользователей,
очереди и сообщения при пересоздании контейнера.

RustFS bucket user-files приватный, versioning не включён. Upload и Download
используют разные ключи и IAM-политики. Download запрещены PutObject и
DeleteObject. Для bootstrap применяется официальный RustFS CLI v0.1.36;
его кэш находится в `.runtime/tools/` вне Git. Административная авторизация
передаётся CLI через окружение одноразового exec, в исходники не записывается.

## Сессии скачивания после аварии

Для download-api используется kernel flock на файле в общей bind-папке
`.runtime/download`. Блокировка удерживается весь срок жизни процесса.
Второй API не может занять её, пока первый ещё жив, включая остановленный
или потерявший связь с PostgreSQL процесс. У блокировки нет таймера аренды.

После завершения предыдущего процесса новый API получает блокировку,
отмечает оставшиеся ACTIVE-сессии FAILED и только затем принимает запросы.
Worker видит отсутствие активных сессий и завершает согласование удаления.
Это проверенный single-host механизм: ровно один Uvicorn-процесс Download API,
общая локальная файловая система для блокировки. Для нескольких хостов или
реплик необходим отдельный проект протокола fencing; данная конфигурация
на такой режим не рассчитана.

## Частично успешные загрузки

Перед PutObject S2 фиксирует UploadIntent. API удерживает отдельную kernel
блокировку UUID до окончания записи объекта и commit метаданных. Worker
получает блокировку только у уже прекратившейся операции, сверяет B2 и удаляет
объект без метаданных. После успешного commit File intent удаляется атомарно.
При недоступном RustFS компенсация повторяется после восстановления.
Общие блокировки API/Worker находятся в `.runtime/upload`.

## RabbitMQ и диагностика

Топология создаётся администраторским bootstrap до начала публикации:
exact bindings, durable topic exchange/queues, persistent сообщения, retry
через TTL 5 секунд и собственные DLQ. До пяти повторов, затем DLQ. ACK после
commit или подтверждённого переноса в retry/DLQ. Повторная публикация Outbox
сохраняет event_id, обработчики учитывают event_id и download_id.

Приложения используют отдельные AMQP-аккаунты с чтением своей очереди.
Configure ограничен доменным exchange и собственными очередями; write —
собственными техническими очередями/default exchange и публикацией доменных
событий только у S1–S3. Топологию всех сервисов создаёт отдельный bootstrap.
Worker readiness падает при потере БД/брокера. Независимые HTTP-функции
продолжают работать. Для проверки использовать `docker compose ps` и логи.

Fault-check намеренно отправляет событие event_version=999. Оно остаётся в
`reports.events.dlq`, подтверждая отсутствие бесконечного requeue. Не удалять
реальные DLQ без анализа; тестовое сообщение можно отличить по версии 999.

Постоянные данные находятся в Docker volumes четырёх PostgreSQL, RabbitMQ
и RustFS. `.runtime/` хранит технические блокировки и CLI. Не удалять и не
заменять файлы блокировок, пока соответствующие API/Worker работают.
