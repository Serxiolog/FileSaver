# AMPIS — S2 Upload Service — специализированный промпт v1.0

**Компонент:** S2 — Upload Service. **Статус:** спецификация для будущей независимой реализации, не программный код. **Дата:** 2026-11-18.

## 0. Применение и документы

Ты — Python/FastAPI backend-разработчик, реализующий **только S2** системы AMPIS. До реализации прочитай: `MASTER_PROMPT_v1.3.md`, `REST_API_CONTRACTS_v1.0.md`, `EVENT_CONTRACTS_v1.0.md`, `RABBITMQ_ARCHITECTURE_v1.0.md`, `OBJECT_STORAGE_ARCHITECTURE_v1.0.md`.

Точные REST/Event Contracts канонические. Не меняй их самостоятельно, не реализуй S1/S3/S4/G1 вместо S2, не используй чужие PostgreSQL. Если задача — проектирование, **не генерируй код** до прямого запроса. Документ описывает один микросервис с API и Worker, использующими общую B2.

## 1. Ответственность и технологическая база

S2 — **единственный владелец метаданных и жизненного цикла файлов**: разрешает авторизованную загрузку, пишет байты в RustFS, хранит владельца, принимает запрос удаления, организует безопасное удаление с S3 и публикует доменные события. S2 не обслуживает скачивание, не считает просмотры/скачивания, не строит каталог и не читает пользователей из B1.

- FastAPI; Pydantic; SQLAlchemy 2.x AsyncSession + psycopg 3 async; Alembic; отдельная PostgreSQL **B2**.
- `aio-pika` и RabbitMQ; отдельные `upload-api` и `upload-worker` из одного Docker-образа.
- S3-compatible RustFS через `boto3` и отдельные **S2 credentials** (PutObject, DeleteObject, HeadObject; GetObject только при необходимости). Bucket `user-files` **private**, key=`files/{file_uuid}`, versioning выключено.
- `boto3` синхронный: не блокировать event loop асинхронного HTTP/Worker; пользоваться thread pool или корректным синхронным слоем.
- Проверять JWT RS256 локально по публичному ключу: `sub` UUID, `exp`, `iss`, `aud`; не доверять внешним `X-User-Id`.

## 2. REST API

| Метод | Внешний путь | Требование | Успех |
|---|---|---|---|
| POST | `/api/files` | JWT, `multipart/form-data`, поле `file` | 201 JSON с `id`, `owner_id`, `original_name`, `size_bytes`, `content_type`, `status=ACTIVE`, `created_at` |
| DELETE | `/api/files/{file_id}` | JWT владельца | 202 JSON с `file_id`, `deletion_request_id`, `status=DELETING`, `message` |

Не создавать дополнительный публичный endpoint получения метаданных: `GET /api/files/{id}` принадлежит S4. Не создавать публичный endpoint чтения содержимого: он принадлежит S3. В HTTP-ответах **не возвращать** `storage_key`, credentials или S3 endpoint.

Лимит содержимого — **1 048 576 байт включительно**. Реально считать байты файла в S2; `Content-Length` или браузерную валидацию не считать достаточной защитой. Поле `owner_id` вычислять только из проверенного JWT, не получать из body. У одинаковых пользовательских имён файлов должны быть разные UUID/keys. Нельзя доверять имени файла при формировании пути, заголовков и метаданных.

Ошибки строго в формате `{ "error": { "code": "...", "message": "...", "request_id": "uuid" } }`. 401 отсутствие/невалидность токена, 403 чужой файл, 404 неизвестный, 413 превышение размера, 422 ошибка валидации, 503 зависимость недоступна. На стадии удаления `202` и повторное использование актуального `deletion_request_id`; точная политика DELETE после DELETED отмечена как деталь согласования, см. канонический REST Contract.

## 3. Модель B2

**File**:

| Поле | Правило |
|---|---|
| `id` UUID PK | Генерируется S2; основа `storage_key` |
| `owner_id` UUID | Получен из JWT `sub`, логическая ссылка на пользователя без внешнего FK |
| `original_name` | Исходное пользовательское имя, безопасно сохранённое как метаданные |
| `storage_key` | Уникальный `files/{file_uuid}` |
| `size_bytes`, `content_type`, `checksum_sha256` | Метаданные/контроль целостности |
| `status` | `ACTIVE → DELETING → DELETED` |
| `version` | Монотонная версия состояния: создание=1, запрос удаления=2, удаление=3 для канонического потока |
| `created_at`, `deletion_requested_at`, `deleted_at` | UTC |
| `deletion_request_id` | Сохраняется при переходе в DELETING для проверки актуального подтверждения S3; служебное уточнение реализации |

**OutboxEvent**: надёжная публикация события из транзакции B2. **ProcessedEvent** с уникальным `event_id`: идемпотентное получение `file.deletion.ready`. Для состояния физического удаления предусмотреть устойчивый recovery-механизм, переживающий аварийное завершение между `DeleteObject` и commit `DELETED` (повторная проверка/идемпотентный DeleteObject). Конкретные индексы и флаги — детали реализации, не внешний контракт.

Никакой общей транзакции PostgreSQL+Object Storage **не существует**; нужно компенсировать частично успешные операции.

## 4. RabbitMQ: точные события

Основной durable topic exchange `domain.events`, `routing_key=event_type`, UTF-8 JSON, persistent. `aio-pika.connect_robust`, Publisher Confirms, mandatory routing, manual ACK после commit, Outbox и дедупликация.

| Направление | Событие | Партнёры |
|---|---|---|
| Публикация | `file.created` | S3 + S4 |
| Публикация | `file.deletion.requested` | S3 + S4 |
| Получение из `upload.events` | `file.deletion.ready` | от S3 |
| Публикация | `file.deleted` | S3 + S4 |

Поля JSON **не менять**, см. `EVENT_CONTRACTS_v1.0.md`. Для состояний файла `aggregate_version` монотонен; `file.created` включает `file_id`, `owner_id`, `original_name`, `size_bytes`, `content_type`, `storage_key`, `created_at`. `file.deletion.requested` и `file.deleted` включают `file_id`, `deletion_request_id` и соответствующую дату; `file.deletion.ready` — `file_id`, `deletion_request_id`, `aggregate_version=null`. `payload.version` не добавлять. В событиях нет бинарных данных или JWT.

С2 Worker — **Consumer + Outbox Publisher**: две управляемые async-задачи одного процесса допустимы. Consumer должен валидировать текущие status и deletion_request_id, предотвращать повторную физическую операцию и сохранять `processed_events` с локальными изменениями одним commit. **Внешний DeleteObject нельзя считать частью SQL-транзакции**; переходы и фоновое восстановление должны позволять повтор без потери подтверждения и без преждевременного `file.deleted`.

## 5. Загрузка: последовательность и сбои

1. G1 передаёт файл и JWT; S2 самостоятельно проверяет JWT.
2. S2 проверяет реальный поток ≤1 048 576 байт, вычисляет UUID, неизменяемый `storage_key`, размер и SHA-256.
3. S2 выполняет `PutObject` в `user-files`. При ошибке RustFS успешного ответа и события `file.created` нет.
4. После успешной записи объекта S2 в одной SQL-транзакции создаёт `File(status=ACTIVE, version=1)` и запись Outbox `file.created`.
5. HTTP 201 означает локальный успех S2, **не** мгновенную готовность каталога S4 или реестра S3: допускается eventual consistency.
6. Worker публикует Outbox в RabbitMQ; если брокер недоступен, событие остаётся в B2.
7. Если RustFS сохранил объект, но commit B2 не удался, предусмотреть компенсационное удаление или безопасный механизм обнаружения/очистки orphan object.

Не выполнять синхронный запрос S3/S4 для регистрации файла; иначе сломаются проверки отказоустойчивости.

## 6. Безопасное удаление: обязательный протокол

**Только владелец** вправе удалить файл: `JWT.sub == File.owner_id` на стороне S2.

1. DELETE владельца → SQL-транзакция меняет `ACTIVE → DELETING`, фиксирует уникальный `deletion_request_id`, увеличивает `version` и в **том же commit** записывает `file.deletion.requested` в Outbox. Ответ `202 Accepted`.
2. S3 из события переходит `AVAILABLE → DRAINING`, не начинает новые скачивания и дожидается безопасного завершения зарегистрированных активных передач.
3. S3 публикует `file.deletion.ready` с тем же **актуальным** `deletion_request_id`; только после получения этого подтверждения S2 разрешено физически удалять объект из RustFS.
4. S2 выполняет `DeleteObject`, с безопасными повторами после временного отказа. Лишь после подтверждённого/идемпотентно завершённого удаления переводит B2 в `DELETED`, увеличивает `version`, публикует `file.deleted` через Outbox.
5. Повторный DELETE при `DELETING` не создаёт новую операцию. Повторное/устаревшее `file.deletion.ready` не должно приводить к преждевременному удалению.

**Критический инвариант:** пока S3 не подтвердил, что реально активные передачи завершены и новые запрещены, S2 **не** вызывает `DeleteObject`. Если S3 выключен, удаление ожидает; upload других файлов работает. Если RustFS выключен, статус остаётся DELETING и повтор продолжается после восстановления. Старое подтверждение не должно давать удалить новый объект/неактуальную попытку.

## 7. Доступ и инфраструктура

- S2 использует только B2 и RustFS; S1 не нужен для определения `owner_id`, S3 не нужен для upload.
- Контейнер `upload-api` обслуживает HTTP; `upload-worker` читает `upload.events` и публикует Outbox. Не запускать неуправляемый Consumer на каждый веб-процесс FastAPI.
- У B2, RabbitMQ и RustFS отдельные переменные окружения и credentials; никогда не использовать root-учётную запись RustFS в приложении. Доступ к PostgreSQL B2 только у S2 API/Worker.
- Миграции независимые; volume B2 постоянный; сервисы и worker устойчивы к перезапускам зависимостей.
- Удаление и загрузка логируются по `request_id`, `file_id`, `event_id`, но не по содержимому файла/секретам.

## 8. Базовые функциональные тесты

- Загрузка с действительным JWT: 201, метаданные B2 и объект RustFS совпадают.
- Нет JWT → 401; >1 МиБ → 413; два файла с одинаковым именем получают разные ключи.
- `file.created` соответствует Event Contract, Outbox переживает временный отказ RabbitMQ.
- Свой DELETE → 202 DELETING; чужой → 403; повторный во время DELETING возвращает ту же операцию.
- После DELETE **до** `file.deletion.ready` байты физически остаются.
- Актуальный ready → физическое удаление → `file.deleted`; дубликат или устаревший ready безопасен.
- Недоступные S3, S4 не препятствуют загрузке; сбой RustFS не создаёт ложного `file.created`.
- Частично успешная запись Object Storage + неуспешная БД имеет безопасное восстановление.

## 9. Готовность к интеграции

S2 независимо развёртывается, владеет B2, использует только разрешённые операции RustFS, публично реализует лишь два утверждённых HTTP-маршрута, публикует три своих типа событий и потребляет только `file.deletion.ready`, поддерживает без потери данные Outbox и безопасное удаление с S3.

**Детали для выбора при реализации, без нового запроса сейчас:** стратегия обработки пустого файла, безопасная компенсация orphan object, точная retry/DLQ-политика, поведение DELETE после окончательного удаления, точные версии образов и healthcheck. Не менять общие контракты при принятии технических решений.
