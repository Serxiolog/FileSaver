# AMPIS — G1 Flask Gateway + Web UI — специализированный промпт v1.0

**Компонент:** G1 — единая HTTP-точка входа и серверный веб-интерфейс. **Статус:** спецификация для будущей независимой реализации, не программный код. **Дата:** 2026-11-18.

## 0. Как использовать

Ты — Python/Flask-разработчик, реализующий **только G1** проекта AMPIS. До проектирования/реализации используй: `MASTER_PROMPT_v1.3.md`, `REST_API_CONTRACTS_v1.0.md`, `EVENT_CONTRACTS_v1.0.md` (для понимания асинхронной модели, но G1 событий не потребляет), `RABBITMQ_ARCHITECTURE_v1.0.md`, `OBJECT_STORAGE_ARCHITECTURE_v1.0.md`.

**Главное:** Flask Gateway — самостоятельное приложение **без собственной бизнес-БД**, совмещающее API Gateway и HTML Web UI (BFF). Не реализуй S1–S4 или их таблицы в G1. Не генерируй программный код до прямого запроса пользователя на реализацию; сначала при необходимости предоставь структуру и план.

## 1. Назначение и ограничения

G1 — **единственная публичная HTTP-точка входа**. Он принимает внешние запросы, обслуживает HTML-страницы Jinja2, проверяет JWT, правильно маршрутизирует обращения к S1–S4 по внутренним Docker адресам, передаёт защищённый identity context через проверенный JWT, возвращает ответы и преобразует ошибки транспортного уровня.

G1 **не имеет** прямого доступа к B1/B2/B3/B4, RabbitMQ или RustFS; не публикует события, не считает скачивания, не хранит метаданные и не удаляет файлы самостоятельно. Бизнес-проверки остаются у соответствующих FastAPI-сервисов. G1 не использует прямые S3/presigned URL.

Технологии: **Flask + Jinja2 + HTML/CSS/необходимый минимальный JS**, Python. Для внутренних HTTP-вызовов использовать поддерживаемый клиент, например `httpx`; Flask сам по себе не обязан быть асинхронным. Вся система развёртывается в **одном Git-репозитории** и Docker Compose с утверждёнными **15** контейнерами (G1 — один из них). Не вводи дополнительный контейнер прокси или новую бизнес-службу без отдельного решения.

## 2. Разделение публичных путей

- `/api/*` — внешняя JSON/REST поверхность, строго согласно `REST_API_CONTRACTS_v1.0.md`.
- `/app/*` — серверные Flask/Jinja2 страницы и HTML-формы, которые обращаются к S1–S4 **через G1**.
- Внешние URL на RustFS, PostgreSQL, RabbitMQ Management UI или внутренние FastAPI-сервисы не публикуются.
- Внешние публичные запросы (каталог, карточка, скачивание) работают **без входа** и при недоступном S1.

**Точная матрица маршрутизации:**

| Метод | Внешний REST URL | Целевой FastAPI |
|---|---|---|
| POST | `/api/auth/register` | S1 Auth |
| POST | `/api/auth/login` | S1 Auth |
| GET | `/api/users/me` | S1 Auth |
| PATCH | `/api/users/me` | S1 Auth |
| POST | `/api/files` | S2 Upload |
| DELETE | `/api/files/{file_id}` | S2 Upload |
| GET | `/api/files/{file_id}/download` | S3 Download |
| GET | `/api/files` | S4 Reports |
| GET | `/api/files/{file_id}` | S4 Reports |
| GET | `/api/files/{file_id}/stats` | S4 Reports |

**Учитывать метод + путь**, поскольку `GET /api/files` и `POST /api/files` обслуживаются **разными сервисами**. Более конкретные маршруты (`/download`, `/stats`) не должны ошибочно попадать в обработчик карточки. Внутренние FastAPI пути могут иметь свой namespace при сохранении внешних контрактов — тогда G1 содержит явное соответствие, но не меняет внешний API.

## 3. HTML/Jinja2 интерфейс

Реализуй простой удобный Web UI без отдельного SPA/frontend-сервера. Предлагаемые страницы (внутренние HTML URL, а не новые REST-контракты):

- Публичный каталог со строками: имя файла, имя владельца, количество скачиваний, ссылка на подробности и отдельная ссылка на скачивание.
- Публичная карточка файла по UUID **без** чтения бинарного содержимого и без изменения счётчика.
- Формы регистрации, входа и редактирования собственного `display_name`.
- Форма загрузки файла (только для авторизованных).
- Управление собственным файлом: удаление с отображением промежуточного `DELETING` (HTTP 202; не обещать мгновенного физического удаления).
- Просмотр владельцем отчёта: общее `download_count` и имена уникальных зарегистрированных скачавших пользователей — строго по ТЗ.
- Понятные сообщения при недоступности отдельного сервиса, без общего падения всего сайта.

Точные названия подмаршрутов `/app/...`, структура шаблонов и оформление HTML могут определяться при реализации G1: они **не** должны менять согласованные `/api/...`.

## 4. Аутентификация, сессия браузера, CSRF

- S1 проверяет пароль и выдаёт JWT; G1 **не** хеширует пароль вместо S1, не имеет прямого доступа к password_hash, не подписывает пользовательские JWT.
- Регистрация/вход через браузер передают пароль по **HTTPS** до G1; G1 пересылает его S1 по защищённому внутреннему соединению/изолированному Docker-каналу в согласованном формате. Не записывать пароль в логи и не сохранять его в Flask session.
- В сценарии `/app/login` G1 вызывает S1, получает `access_token`, устанавливает браузеру **HttpOnly** cookie, `Secure` при HTTPS, подходящий `SameSite` и ограниченные срок/область действия. JWT действителен **3600 секунд**; refresh token в v1 нет.
- Для внешних программных клиентов `POST /api/auth/login` должен сохранять утверждённый REST JSON-ответ `{access_token, token_type, expires_in}`. Для HTML-формы G1 устанавливает cookie самостоятельно, не раскрывая JWT пользовательскому JavaScript.
- Для защищённого API G1 берёт JWT из `Authorization: Bearer` либо из cookie, **самостоятельно** проверяет RS256-подпись, `exp`, `iss`, `aud`, валидность UUID `sub`; затем передаёт JWT целевому сервису через **внутренний** `Authorization` header.
- Если одновременно представлены противоречащие способы аутентификации, применить безопасную явно описанную политику, чтобы не произошло смешение идентичностей. Внешние произвольные `X-User-Id` или аналогичные headers **не** считать доказательством идентичности и не пробрасывать как доверенные.
- У S1–S4 собственная валидация JWT и проверка бизнес-прав. G1 **не** имеет права считать проверку JWT достаточной для удаления чужого файла или закрытого отчёта.
- Для любых браузерных изменяющих запросов с cookie (включая `/api` при cookie auth) необходима **CSRF-защита**. `SameSite` — дополнительная защита, не замена CSRF token/эквивалента. Для запросов с явным Bearer токеном, не основанных на cookies, отдельно оценить CSRF threat model.
- В production внешнее соединение обязательно HTTPS. HTTP на `localhost` внутри учебной среды разрешается только как сознательное локальное исключение; не выдавать его за TLS-защиту. Модель TLS-терминации/внутреннего транспорта должна быть описана в окружении развёртывания, без молчаливого введения шестнадцатого контейнера.
- Выход из браузерной сессии может очищать cookie через HTML-обработчик G1, но в v1 нет мгновенного отзыва уже выданного JWT; logout не требует нового REST-контракта S1.

## 5. Проксирование HTTP, multipart и скачивание

**JSON:** G1 проксирует согласованные запросы к нужному сервису и возвращает точные status, JSON и поддерживаемые HTTP headers без самовольного изменения схемы. Ошибки FastAPI валидации приводятся к общему контракту `{ "error": { "code", "message", "request_id" } }`.

**Upload:** G1 принимает `multipart/form-data` (поле `file`) и передаёт его в S2 без искажения байтов; не определяет `owner_id` из формы. Ограничение **байтов самого файла** 1 048 576 в S2, в G1 учитывается небольшая multipart-обёртка. При превышении возвращать 413 в едином формате. Не считать клиентский `Content-Length` достаточным.

**Download:** `GET /api/files/{file_id}/download` передаётся **S3**; G1 возвращает клиенту его **бинарный поток** со статусом, Content-Type, безопасным Content-Disposition и, если корректно, Content-Length. Не преобразовывать скачивание в JSON и не отдавать файл из RustFS напрямую. Закрывать HTTP-ресурсы при прерывании клиента, по возможности сигнализировать прерывание upstream S3. Учёт успешной передачи — ответственность S3. Избегать полной буферизации, несмотря на небольшой размер 1 МиБ.

**Meta:** `GET /api/files/{file_id}` маршрутизируется **S4**, не S3, и не увеличивает счётчик скачиваний. `download_url` указывает только на публичный G1 маршрут, не на внутренний адрес S3/RustFS.

Таймауты должны быть разумными; для streaming route отдельно учесть более длительную передачу и внезапный разрыв соединения. При недоступном upstream отвечать 503 `SERVICE_UNAVAILABLE` в стандартном JSON для ещё не начавшегося ответа; после начала передачи байтов нельзя обещать корректный JSON-ответ вместо прерванного потока.

## 6. Разделение ошибок и отказов

- S1 недоступен: регистрацию/логин/профиль временно не обслуживаем, **но** публичные каталог, карточки и скачивание продолжают работать. Ранее выданные действительные JWT могут проверяться без вызова S1.
- S2 недоступен: upload/delete временно 503; список S4 и известные S3 файлы доступны.
- S3 недоступен: скачивание временно 503; список/карточки S4 и операции S1/S2 доступны.
- S4 недоступен: каталог/карточка/отчёт 503; авторизация, загрузка и скачивание продолжают работать.
- RabbitMQ и RustFS недоступны: G1 сам с ними **не взаимодействует**; отображает статусы соответствующих целевых FastAPI-сервисов.
- G1 как единая точка входа может быть общей точкой отказа: это заданный компромисс учебной архитектуры, не создавать сложный кластер без запроса.

Не превращать технический timeout одного сервиса в «падение всей системы» и не делать глобальный healthcheck всех сервисов условием обслуживания публичного каталога.

## 7. Предлагаемая структура проекта G1

```text
gateway/
  app.py                # Flask app factory / точка запуска
  web/                  # Blueprint: HTML-страницы /app/*
  api/                  # Blueprint: REST-маршруты /api/*
  auth/                 # JWT cookie, проверка подписи и CSRF
  clients/              # HTTP-клиенты S1–S4, timeouts, streaming
  templates/            # Jinja2
  static/               # CSS / минимум JS
  tests/                # pytest + Flask test client / HTTPX для mock upstream
  Dockerfile
```

Это **рекомендация организации**, а не дополнительный сервис или требование к файловым именам. G1 не создаёт ORM-моделей B1–B4 и собственных миграций Alembic.

Секреты Flask и JWT public key поставляются конфигурацией; приватный ключ RS256 никогда не находится у G1. Адреса S1–S4 настраиваются через environment. Приложение и внутренние вызовы должны корректно завершаться, закрывая HTTP-соединения и streaming-ответы.

## 8. Базовые функциональные тесты

- Сопоставление всех **10** внешних HTTP-маршрутов именно со своими S1–S4; `GET` и `POST /api/files` должны идти в разные сервисы.
- Публичные каталог/карточка/скачивание доступны без JWT.
- Flask login устанавливает HttpOnly cookie с согласованными флагами; Bearer REST login сохраняет утверждённый JSON без лишних обёрток.
- JWT невалиден/истёк → 401; нет подмены личности через `X-User-Id`; S1 не вызывается при проверке JWT.
- CSRF-защита изменяющих cookie-запросов.
- Upload сохраняет байты multipart, превышение лимита отклоняется.
- Download передаёт бинарный поток и headers, а просмотр карточки не вызывает скачивания.
- При отключении S1 остаются публичные S3/S4 маршруты; при отключении S4 upload и download продолжают работать.
- Ошибки недоступного upstream и ошибки валидации имеют единый JSON-формат с `request_id`.

## 9. Готовность к интеграции

G1 независимо стартует в своём контейнере, имеет один HTTP-порт для внешнего доступа, предоставляет 10 утверждённых REST-маршрутов и HTML-интерфейс, не хранит бизнес-данные, правильно работает с безопасным cookie/Bearer JWT, отделяет метаданные от скачивания и не создаёт зависимости публичных функций от работоспособности S1.

**Открытые детали при реализации:** точные URL HTML-страниц, CSS, сервер запуска Flask, конкретный HTTP client и таймауты, выбор CSRF-техники, схема настройки HTTPS/TLS для локальной и внешней среды, стратегический выбор реакции на два одновременно переданных credentials. Они **не меняют** утверждённую архитектуру или JSON-контракты.
