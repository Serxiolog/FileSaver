# AMPIS — S4 Reports & Search Service — специализированный промпт v1.0

**Компонент:** S4 — Reports & Search Service. **Статус:** спецификация для будущей независимой реализации, не программный код. **Дата:** 2026-11-18.

## 0. Использование и источники истины

Ты — Python/FastAPI-разработчик, реализующий **только S4** проекта AMPIS. Перед работой применяй `MASTER_PROMPT_v1.3.md`, `REST_API_CONTRACTS_v1.0.md`, `EVENT_CONTRACTS_v1.0.md`, `RABBITMQ_ARCHITECTURE_v1.0.md`. Последние два контракта канонические для соответствующих форматов.

S4 разрабатывается как независимый **read-model / projection** сервис. Не создавай SQL-зависимостей от B1/B2/B3, не вызывай S1/S2/S3 по HTTP для построения выдачи и не сканируй RustFS для каталога. Не меняй поля контрактов и не создавай публикацию собственных бизнес-событий. Не генерируй код, пока пользователь прямо не запросит реализацию.

## 1. Ответственность

S4 обслуживает:

- Публичный список доступных файлов, поиск по имени файла и отображаемому имени владельца, сортировку и пагинацию.
- Отдельную публичную карточку файла **без скачивания** и без увеличения счётчика.
- Отображение количества успешных скачиваний, включая анонимные.
- Закрытый **для владельца** отчёт: общий `download_count` и имена **уникальных зарегистрированных** скачивавших пользователей.
- Обновление локальной PostgreSQL B4 **только** на основе событий RabbitMQ S1/S2/S3.

S4 **не** обслуживает загрузку/скачивание бинарного содержимого, не выдаёт JWT и не публикует доменные сообщения. При недоступности RabbitMQ или S1/S2/S3 S4 должен продолжать отдавать **последнее сохранённое состояние**, не обращаться синхронно за обновлениями.

## 2. Стек и контейнеры

- FastAPI, Pydantic, SQLAlchemy 2.x AsyncSession, psycopg 3 async, собственная PostgreSQL **B4**, Alembic.
- RabbitMQ `aio-pika.connect_robust`, durable `domain.events` topic, очередь `reports.events`.
- Два контейнера одного сервиса и Docker-образа: `reports-api` и `reports-worker` (только Consumer). Нет Outbox Publisher S4 в v1, поскольку S4 не публикует событий.
- JWT RS256: независимо проверять подпись, срок, `iss`, `aud`, `sub` на `GET /api/files/{file_id}/stats`; открытые GET не требуют JWT.
- pytest + HTTPX, при необходимости pytest-asyncio; базовые функциональные тесты и сценарии повторной/изменённой последовательности событий.

## 3. REST API S4

| Метод | Внешний путь | Назначение | Доступ |
|---|---|---|---|
| GET | `/api/files` | Каталог, поиск, сортировка, пагинация | Публичный |
| GET | `/api/files/{file_id}` | Метаданные отдельного файла | Публичный |
| GET | `/api/files/{file_id}/stats` | Отчёт по своему файлу | JWT владельца |

**Точные поля ответов берутся из `REST_API_CONTRACTS_v1.0.md` и не меняются:**

- Элемент каталога и карточка: `id`, `original_name`, вложенный `owner: { id, display_name }`, `size_bytes`, `download_count`, `download_url` (маршрут G1 `/api/files/{id}/download`), `created_at`.
- Каталог: `{ "items": [...], "page": 1, "size": 20, "total": 0, "pages": 0 }` (для пустого результата); `total` — число элементов по фильтру, `pages` — число страниц.
- Отчёт: `{ "file_id": "uuid", "original_name": "...", "download_count": 42, "downloaded_by": [{"user_id":"uuid", "display_name":"..."}] }`. Повторы скачиваний включены в `download_count`, но один зарегистрированный человек фигурирует в `downloaded_by` только один раз; анонимные люди в список имён не добавляются.

**Параметры каталога:** `name` — поиск подстроки имени; `owner` — поиск подстроки отображаемого имени; `sort=name|owner|downloads`; `order=asc|desc`; `page>=1`; `size=1..100`; defaults `page=1`, `size=20`, `sort=name`, `order=asc`. В случае одинакового значения сортировки дополнительный ключ `file_id` для детерминированного порядка.

Публичная карточка/каталог доступны без JWT, **не** создают DownloadHistory. После обработки `file.deletion.requested` соответствующий файл **скрывается** из публичной выдачи. `GET /api/files/{id}` для неизвестного/скрытого файла → 404. Для `/stats` сравнить `JWT.sub` с `FileCatalogProjection.owner_id`, а не обращаться к S2. Ошибки единообразны: `{ "error": { "code": "...", "message": "...", "request_id": "uuid" } }`.

## 4. Модель B4 (читаемые проекции)

**UserProfileProjection**:

| Поле | Смысл |
|---|---|
| `user_id` UUID PK | Идентификатор из S1 |
| `display_name` | Последнее подтверждённое имя |
| `version` | Последняя `aggregate_version` пользователя |

**FileCatalogProjection**:

| Поле | Смысл |
|---|---|
| `file_id` UUID PK | Идентификатор файла из S2 |
| `owner_id` | Идентификатор владельца без FK к B1 |
| `filename` / `original_name` | Для поиска, сортировки и ответа API |
| `size_bytes` | Для карточки |
| `status` | ACTIVE / DELETING / DELETED (или эквивалентные значения проекции) |
| `version` | Последняя `aggregate_version` файла |
| `created_at` | Время загрузки |
| `download_count` | Число уникально обработанных успешных скачиваний |

**FileDownloadProjection**: `download_id` unique, `file_id`, `user_id NULL`, `downloaded_at`; достаточна для расчёта количества и списка уникальных зарегистрированных скачивавших.

**ProcessedEvent**: `event_id` unique, чтобы повторная доставка одного сообщения не применялась повторно. Добавить индексы для поиска/sort/owner_id и уникальность download_id. Нет cross-database foreign keys. Внутренняя стратегия хранения tombstone для файлов, чьи события пришли не в порядке, обязательна; она не должна добавлять поля в публичный JSON.

Для случая, когда событие скачивания приходит **до** `file.created`, сохранить сам факт с `download_id` и впоследствии корректно связать его с проекцией файла, не потеряв счётчик. Конкурентные Worker не должны допускать lost updates.

## 5. Входящие события RabbitMQ

S4 получает из **своей** очереди `reports.events` шесть типов событий:

| Издатель | Событие | Изменение B4 |
|---|---|---|
| S1 | `user.registered` | Создание/обновление профиля v1 |
| S1 | `user.renamed` | Обновление имени только по более новой версии |
| S2 | `file.created` | Добавление метаданных файла/владельца |
| S2 | `file.deletion.requested` | Скрытие из публичного каталога |
| S2 | `file.deleted` | Фиксация факта удаления/tombstone |
| S3 | `file.downloaded` | Уникальный факт скачивания, увеличение счётчика один раз |

**S4 не получает `file.deletion.ready`**: это внутреннее подтверждение S3→S2. Он не публикует доменные события в v1.

Точные JSON по `EVENT_CONTRACTS_v1.0.md`. Оболочка `event_id`, `event_type`, `event_version`, `aggregate_id`, `aggregate_version`, `occurred_at`, `correlation_id`, `payload`. Не добавлять `payload.version`. Содержимое файлов и ключи секретов не требуются.

Обработка Consumer: валидировать контракт → в **одной транзакции B4** проверить/записать уникальный `event_id` и применить изменения → commit → manual ACK. При повторе ACK без повторного обновления `download_count`. Для факта скачивания дополнительно уникален `download_id`, даже если пришло другое `event_id` с тем же `download_id`.

**Реальный порядок событий может различаться:**

- `user.renamed` до `user.registered` не должен сбросить отображаемое имя на старое.
- `file.deletion.requested` или `file.deleted` до `file.created` должны сохранить tombstone и не открыть файл снова.
- `file.downloaded` до `file.created` должен учитываться после формирования каталога.
- Переотправка того же события не изменяет результаты; `file.downloaded` для анонимного пользователя учитывает `null` без имени в `downloaded_by`.

Временные ошибки — ограниченные повторы с задержкой; невалидные схемы/невосстановимые ошибки — DLQ `reports.events.dlq` по общей политике RabbitMQ. Никакого бесконечного `nack(requeue=True)`.

## 6. Порядок обработки запросов

1. Каталог: B4-выборка активных FileCatalogProjection; применить `name` и `owner` фильтры, сортировку, вторичный UUID-ключ, пагинацию и `total`.
2. Публичная карточка: локально проверить ACTIVE, объединить проекцию файла с локальным UserProfileProjection; вернуть согласованные поля без обращения к B1/B2/B3.
3. Статистика: проверить JWT → локально удостовериться в существовании файла и его `owner_id` → вычислить из B4 `download_count` и список уникальных зарегистрированных `user_id` → подставить последние известные `display_name` из собственной проекции пользователя.
4. Возможное отсутствие имени из-за delayed user event обрабатывается как временная eventual-consistency ситуация, не выдумывать пользователя и не ходить в S1. Детальное поведение placeholder определяется при реализации и документируется.

## 7. Сценарии отказов

- S4 API доступен, а RabbitMQ недоступен: возвращает последнее B4 состояние.
- `reports-worker` отключён: сообщения должны оставаться в durable `reports.events`; после восстановления Worker обрабатывает backlog автоматически.
- S1 отключён: каталог/статистика по уже известным пользователям продолжает работать без S1.
- S2 отключён: каталог/карточка работают по B4, пока другие сервисы продолжают независимо функционировать.
- S3 отключён: каталог/поиск/прошлая статистика остаются доступны; новых `file.downloaded` не будет до восстановления скачивания.
- Повторное или позднее событие не должно искажать счётчик, имена или статус файла.

Не трактовать eventual consistency как разрешение терять события: состояние обязано догонять после восстановления доставки.

## 8. Внутренняя структура, Docker, тесты

Рекомендуемые каталоги: `api/`, `schemas/`, `db/`, `projections/`, `messaging/` (Consumer/Inbox), `alembic/`, `tests/`. Сервис не имеет прямого доступа к RustFS и не нуждается в S3 credentials.

`reports-api` и `reports-worker` используют одну B4 и независимые команды запуска; worker подключается к RabbitMQ и B4. Все данные конфигурируются через переменные окружения; SQL-модели только S4, секреты не в Git. Health/readiness отличает API, БД и соединение Worker с RabbitMQ.

**Базовые функциональные тесты:**

- Каталог: `name`, `owner`, сортировка по имени/владельцу/скачиваниям, `asc|desc`, `page/size`, стабильный порядок и пустая страница.
- Карточка GET не влияет на `download_count`.
- Отчёт владельцу: число включает все завершённые события скачиваний, список содержит лишь уникальных зарегистрированных пользователей с актуальным именем; гость учтён в числе, не в списке.
- Чужой JWT → 403; отсутствующий JWT на `/stats` → 401; публичные GET работают без JWT.
- Обработка каждого из шести событий и версий, отсутствие дубликатов.
- События в обратном порядке и повторная доставка не искажают проекции.
- После паузы `reports-worker` накопленный backlog корректно обрабатывается.

## 9. Готовность к интеграции

S4 независимо запускается и мигрирует B4; предоставляет **три** согласованных HTTP-операции, строит каталог только из своей БД, потребляет ровно необходимые события, формирует статистику строго по ТЗ и восстанавливает состояние после временной остановки очереди.

**Неутверждённые детали для реализации:** обработка отсутствующей локальной проекции имени, SQL-оптимизация запросов и индексов, retry/DLQ настройки, сроки хранения исторических проекций. Они не требуют новых архитектурных компонентов.
